# Dark Mode — Specs & Implementation Plan

Status: **Planned**
Scope: tokens pipeline → CSS output → Tailwind → Storybook preview → component stories
Related: [WORKFLOW.md](../WORKFLOW.md), [CLAUDE.md](../CLAUDE.md)

---

## 1. Goals

- Support a light + dark theme driven by the same token names (`color.*`).
- Zero component-code changes when switching themes — theming happens at the
  CSS-variable level.
- Keep the existing one-directional pipeline intact:

  ```
  Figma → tokens/figma-raw/*.json → tokens/tokens.json
       → dist/css/variables.css   (:root light + [data-theme="dark"])
       → dist/json/tailwind-tokens.json (var() references)
       → dist/json/tokens.json (flat map)
  ```

## 3. Phase plan

### Phase 0 — Acquire dark values (blocked on input)

Choose one:

- **a) Scoped Figma token** *(preferred)* — create a personal access token with
  `File variables: Read`, then read both modes of each variable collection via
  `/v1/files/:key/variables/local`.
- **b) Frame snapshot** — run MCP `get_variable_defs` over the dark frames and
  save to `tokens/figma-raw/dark-theme.json`.

Output: a map `{ "<figma variable name>": { light, dark } }`.

### Phase 2 — Token restructure

- Extend `tokens/tokens.json` so every themed token carries both values:
  ```json
  "background": {
    "error": { "vibrant": { "default": {
      "value": "#f32b36",
      "darkValue": "<dark>",
      "type": "color"
    }}}
  }
  ```
- Naming stays identical across themes; only values differ.
- Non-themed tokens (brand social colors, typography metrics) carry no
  `darkValue`.

### Phase 3 — Build outputs

- `style-dictionary.config.js` → `custom/css-variables`:
  ```css
  :root               { --color-background-error-vibrant-default: #f32b36; }
  [data-theme="dark"] { --color-background-error-vibrant-default: <dark>; }
  ```
- `custom/tailwind-theme`: replace hex color values with
  `var(--color-…)` references so utilities like
  `bg-background-error-vibrant-default` follow the active theme.
- `custom/flat-tokens`: add `theme.dark.<dot.path>` entries alongside
  existing `color.*` keys.

### Phase 4 — Storybook

- Add `@storybook/addon-themes` to `.storybook/main.js` addons.
- `.storybook/preview.js`: decorator setting `data-theme` on `<html>` /
  preview body; toolbar gets a Light/Dark switch.
- Replace hardcoded story backgrounds (`#fafafa`, `#141414`) with
  `var(--color-background-surface-primary)` / semantic equivalents.

### Phase 5 — Verification checklist

- [ ] `npm run tokens:sync` emits both `:root` and `[data-theme="dark"]` blocks
- [ ] Tailwind utility classes resolve to `var()` (inspect built CSS)
- [ ] Toolbar toggle switches themes live in every story
- [ ] Button / LinkButton / playground stories readable in both themes
- [ ] No hardcoded hex left in stories (except brand/social colors)
- [ ] Contrast spot-check on key surfaces (text/surface/error pairs)

## 4. Interim placeholder strategy

Until real Figma dark values land (Phase 0 blocked), a placeholder dark palette
can be generated by script: invert neutral ramps, dim brand vibrants, keep
error hues. Marked clearly as `/* placeholder */` in the CSS output and replaced
wholesale in Phase 3.

## 5. Risks / notes

- **Viewer role**: local (unpublished) variables may be invisible even with a
  scoped token; published library variables are the fallback source.
- **Social brand colors** stay constant across themes by design.
- **Focus rings** hardcode `#ffffff` outer ring in components — should become
  `var(--color-background-static-default)` for dark mode correctness.
